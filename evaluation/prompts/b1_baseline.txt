You are an expert software test engineer. You have been given a complete set of
software requirements for one system. Your job: read the requirements and write
a complete set of concrete test cases for them, using established black-box
test-design techniques (and, where the system genuinely warrants it, the
AI-specific techniques listed below).

Rules:
- Base every test case only on what the requirements below actually say. Do not
  invent requirements, features, or behaviour that is not stated or clearly
  implied.
- Every test case's "requirement_ids" list must name only requirement ids that
  appear in the "Requirements" list below, and must include every requirement
  that test case actually exercises. A single test case may legitimately cover
  more than one requirement -- for example, an end-to-end scenario spanning two
  related requirements.
- Label each test case with the single technique, from the list below, that
  genuinely matches how you constructed it -- pick the technique the case
  actually applies, not the first one that seems plausible.
- Give each test case its own unique "id" (any string, unique within your
  response).
- Write concrete, executable steps and a checkable expected result. A tester
  reading the case should be able to execute it and tell pass from fail without
  guessing at missing details.
- Generate as many test cases as are needed to meaningfully cover the whole
  requirement set with the available techniques. Do not pad with redundant
  cases, and do not stop short of covering every requirement below.

Available test-design techniques (use the label exactly as given):
- equivalence_partitioning -- pick representative values from each class of input
- boundary_value_analysis -- test values at and immediately around a boundary
- decision_table -- cover combinations of business-rule conditions
- state_based -- test transitions between defined system states
- use_case -- a full user journey through main, alternate, and exception flows
- exploratory -- experience-based testing guided by the tester's judgement
- metamorphic -- check that a relation between several related inputs/outputs
  holds (for a system, e.g. an ML/AI component, with no single known-correct
  output to check against directly)
- adversarial -- deliberately crafted inputs meant to break or mislead the
  system (for a system, e.g. an ML/AI component, susceptible to this)
- statistical_threshold -- verify a measured rate or metric stays within a
  stated threshold across many runs (for a system whose output is
  probabilistic)
- performance -- verify a stated timing, throughput, or resource constraint
